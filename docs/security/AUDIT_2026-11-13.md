# BetterDesk — audyt bezpieczeństwa 2026-11-13

Kontynuacja [`AUDIT_2026-10-30.md`](AUDIT_2026-10-30.md). Ten dokument opisuje
przegląd kodu, konfiguracji i wdrożenia z 13 listopada 2026 (gałąź `dev`,
wersja 3.5.233) oraz **stan napraw** wprowadzonych w tej samej sesji.

Zakres: `web-nodejs` (~204k linii JS), `betterdesk-server` (~88k linii Go),
`betterdesk.sh` / `install.sh` / Dockerfiles, workflow GitHub Actions,
konfiguracja hosta testowego `betterdesk-test`.

Metodyka:

- przegląd statyczny w czterech obszarach (auth/RBAC, sinki i wstrzyknięcia,
  serwer Go, wdrożenie/sekreciki/CI);
- weryfikacja dynamiczna na `betterdesk-test` (nagłówki, TLS, próby
  nieuwierzytelnione, rate limiting, manipulacja `Host`, traversal, origin WS);
- `npm audit`, `go build`, `go vet`, `go test ./...`, `govulncheck`,
  `npm run test:security`, pełny `jest`;
- brak testów destrukcyjnych; rekordy testowe w bazie usunięte.

## 1. Znaleziska krytyczne

### C1 — nieuwierzytelniony `POST /api/bd/register`

**Problem.** Endpoint przyjmował żądanie z samym nagłówkiem `X-Device-Id`.
Dowolny host mógł:

- zaśmiecać inwentarz (6 żądań w 0,3 s → 6× `200`, brak limitera),
- przywrócić urządzenie oznaczone `is_deleted = 1`,
- podmienić `pk` istniejącego urządzenia (dowód: `AAAA…` → `ZZZZ9999`).

**Naprawa.** `web-nodejs/routes/bd-api.routes.js` + `lib/enrollmentProof.js`:

- dowód posiadania Ed25519 (`bd-enrollment-v1`, te same nagłówki co serwer Go)
  wymagany przy pierwszej rejestracji i przy każdej zmianie `public_key`/`uuid`,
- `403 device_banned` / `403 device_removed` przed jakimkolwiek zapisem
  (`db.getPeerRegistrationState` w obu adapterach),
- `registerLimiter` — 20 żądań/min/IP (`BD_REGISTER_RATE_LIMIT_MAX`),
- `BD_REGISTER_ALLOW_OPEN=true` jako jawna furtka dla integratorów bez podpisów.

**Testy.** `tests/bd-register.hardening.test.js` — 11 przypadków: brak dowodu,
poprawny podpis, replay nonce, ban, soft-delete, podmiana klucza, rotacja z
dowodem, heartbeat bez narzutu, furtka open, brak `public_key`, flood → 429.

### C2 — `RegisterPk` ze `old_id` bez dowodu tożsamości

**Problem.** `signal/handler.go` akceptował zmianę ID, gdy `msg.Pk` było puste
(serwer brał klucz z bazy), a `UUID` weryfikował tylko dla 16-bajtowych
wartości. Wystarczyła znajomość ID ofiary.

**Naprawa.** Zmiana wymaga teraz **dowodu tożsamości**: zgodnego `pk` albo
zgodnego `UUID` (tak jak hbbs — klient RustDesk wysyła `old_id` bez `pk`, więc
samo `pk` nie może być obowiązkowe). Dodatkowo żądanie jest odrzucane, gdy
adres jest już powiązany z innym peerem (`peerIDBySessionAddr`).

**Testy.** `signal/handler_test.go`: brak dowodu, klucz niepasujący, UUID
niepasujący, zmiana z poprawnym UUID, wiersz bez zapisanego UUID.

### C3 — ścieżka panel → root

**Problem.** Serwer Go działał jako `root`, a katalog danych `/opt/rustdesk`
miał `2775 root:betterdesk` z binarką zapisywalną przez użytkownika konsoli.
Dowolne RCE w panelu = root po restarcie.

**Naprawa.**

- binarka przeniesiona do `/usr/local/bin/betterdesk-server` (`0755 root:root`),
  poza katalogiem zapisywalnym przez usługę;
- `/opt/rustdesk` → `2750` (bez prawa tworzenia/usuwania wpisów przez konsolę);
  pliki, które konsola legalnie aktualizuje (`.env`, `blocklist.txt`,
  `audit.jsonl`, baza), zachowują grupowe prawo zapisu;
- usługa działa jako `betterdesk` (`User=betterdesk`, `NoNewPrivileges=yes`,
  `PrivateTmp=yes`), a `mesh_agent_server.pem` ma właściciela `betterdesk:0600`;
- `DSN` i hasło bootstrapu usunięte z plików `.service` (tylko `EnvironmentFile`
  `0600`);
- `betterdesk.sh` i `scripts/linux-ensure-console-user.js` ustawiają nowe tryby.

**Weryfikacja na hoście.** `systemctl show betterdesk-server -p User` →
`betterdesk`; `ss -lntp` pokazuje 7 portów; `/api/health` i panel → `200`;
podmiana binarki przez użytkownika `betterdesk` → `REPLACE_BLOCKED`.

## 4. Niskie / porządkowe

- `deepmerge` (low, dev-only, brak poprawki upstream) — jawnie zaakceptowane.
- `restartCoordinator` porównuje tokeny przez `crypto.timingSafeEqual`.
- Workflow Actions przypięte do commitów SHA (73 referencje, 13 plików +
  `anchore/sbom-action`), Dependabot pilnuje `github-actions`.
- Trzy wcześniej czerwone testy (`devices.routes`, `users.routes`) naprawione:
  zależność od formatu `::ffff:127.0.0.1` i brakujący mock
  `panelAccessPolicyService`.
- Host testowy: firewall `ufw` aktywny (22, 5000, 5443, 21114-21122, 8000 i 9090
  tylko z LAN), `gohttpserver` ograniczony do LAN.

## 7. Pozostałe do decyzji operatorskiej

Te punkty nie zostały zmienione w kodzie, bo wymagają decyzji produktowej lub
operacyjnej:

1. **M9** — zamiana `requireAdmin` na `requirePermission('server.config')`
   w `network.routes.js` (defence in depth; dziś blokowane przez panel access).
2. **M10** — tokeny gościa wyłącznie z cookie/headera.
3. **M12/M13** — bindowanie portów Docker do `127.0.0.1`, twarde wymaganie
   `PG_PASSWORD`, hardening unit konsoli (`ProtectSystem`, `PrivateTmp`).
4. **M15** — szyfrowanie poświadczeń SMB dla backupów.
5. **H8** — publikacja podpisanego manifestu w release tooling (kod
   weryfikujący jest gotowy; brakuje generatora podpisów w CI).
6. **go1.26.11 na hoście testowym** — zbudowana binarka wymaga wdrożenia przez
   root (panel celowo tego nie robi).
